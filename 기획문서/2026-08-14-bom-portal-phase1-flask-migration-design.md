# 설계 문서 - BOM 재료비 포탈 정식판(PHASE1) Flask 마이그레이션

문서버전: v1.0 (2026-08-14, 브레인스토밍 확정본) · 관련 문서: `BRD.md`, `PRD.md`, `로드맵.md`, `2026-08-13-bom-portal-prototype-plan.md`

## 1. 배경 및 목적

`proto(rev.0)`(Streamlit 프로토타입)에서 업로드/입력그리드/환율/다운로드 기능 검증 완료. 로드맵 PHASE1("각 담당자가 실시간으로 충돌없이 입력 가능한 시스템")을 향한 정식판 마이그레이션 1차 단계로, **Streamlit → Flask 전환 + UI/UX 전문가 수준 재설계 + 로그인 서브시스템 구축**을 진행한다.

**이번 범위**: 기존 프로토타입 기능(업로드/조회·입력/환율/다운로드) + UI/UX 고도화 + 로그인. 로드맵 PHASE1의 SUMMARY 집계, 권한분리(관리자/설계자), 다중사용자 동시입력, 소싱정보·물류정보·차종정보 추가필드는 **이번 범위 아님** — 다음 단계에서 별도 설계/구현.

## 2. 아키텍처

- **Flask + Jinja2 + HTMX + Bootstrap 5**: 서버 렌더링 중심, 그리드/필터는 HTMX로 부분 갱신. React 등 SPA 프레임워크 도입 안 함.
- **SQLite** 유지 (`bom.db`).
- **Flask-Login**으로 실 로그인 구현, 관리자 계정 1개 초기 시드.
- 로컬 실행: `waitress`로 WSGI 서빙. `run.py` 실행 시 브라우저 자동 오픈.
- 기존 순수 파이썬 모듈(`columns.py`, `db.py`, `parser.py`, `fx.py`, `calc.py`, `exporter.py`)은 프레임워크 무관 로직이므로 그대로 재사용. Flask 라우트/템플릿 계층만 신규 추가.
- 작업 위치: 새 폴더 `portal/`. `proto(rev.0)/`는 그대로 보존(참고/롤백용, 더 이상 개발 안 함).
- PHASE2~5 확장 고려: HTMX+Bootstrap 구조는 CRUD/필터/차트 중심의 PHASE2~5 요구사항(버전잠금, 목표가 입력, 변동이력 조회, 비교분석)에 충분히 대응 가능. 실시간 공동편집이 아닌 "충돌 없는 입력"은 DB 트랜잭션/버전 관리로 해결(PHASE2 범위). 추후 진짜 실시간 필요 시 Flask-SocketIO만 추가하면 되고 프레임워크 재작성 불필요.

## 3. 데이터 모델 변경

### 3.1 PK 구조 전환 (기존 한계 수정)
- 문제: 실제 BOM에서 품번 74개가 서로 다른 조립위치(행)에 재사용됨. 기존 `part_no` 단독 PK 구조에서는 재업로드 시 마지막 등장 행만 반영되고 첫 행은 유실됨.
- 해결: `parts`, `purchase_data` 모두 PK/FK를 **`(part_no, row_num)` 복합키**로 전환. `row_num`은 원본 엑셀 행번호(이미 export 좌표 복원용으로 저장 중이던 값)를 그대로 식별자 일부로 사용.
- 영향 범위: `db.py`(스키마, upsert/get/list 함수 시그니처), `parser.py`(upsert 호출부), `exporter.py`(조회 쿼리), `calc.py` 호출부, 관련 테스트 전체(`test_db.py`, `test_parser.py`, `test_exporter.py`, `test_calc.py`).

### 3.2 신규 테이블: `users`
| 컬럼 | 설명 |
|---|---|
| id | PK |
| username | 로그인 아이디 |
| password_hash | 해시된 비밀번호 (werkzeug.security) |
| role | 현재는 `admin` 단일 값만 사용. 권한분리는 이번 범위 아니지만 컬럼은 미리 확보 |
| created_at | 생성일시 |

초기 시드: `flask create-admin <username> <password>` CLI 커맨드로 관리자 계정 생성. 최초 실행 시 자동 생성(기본 비밀번호 하드코딩) 방식은 보안상 사용하지 않음.

### 3.3 기존 DB 처리
- `bom.db`는 스키마 변경으로 재생성. 현재 담긴 322건은 테스트용 파싱 데이터(구매정보 비어있음)라 재생성 동의됨 — `portal/` 폴더에서 빈 DB로 시작, BOM 재업로드로 복원.

## 4. UI/UX 디자인

**톤앤매너**: 밝은 테마 기업용 ERP/포탈 스타일. 배경 밝은 회색(#F5F7FA류), 카드 흰 배경 + 옅은 그림자 + 좌측 포인트컬러 보더. 참고 이미지(APM 대시보드)의 카드형 레이아웃/사이드바 내비게이션 구조는 차용하되 색상 톤만 라이트로 전환.

### 4.1 전역 레이아웃
- 좌측 고정 사이드바: 포탈 로고/명, 메뉴(홈 / BOM 조회·입력 / BOM 업로드 / 환율 관리 / 다운로드), 하단에 로그인 사용자명 + 로그아웃
- 상단 바: 현재 페이지 제목, 우측 상태 뱃지(환율 갱신 상태 등)

### 4.2 홈(대시보드)
- KPI 카드 4개: 총 부품수 / 구매정보 미입력 건수 / 적용환율(USD·EUR) / 최근 업로드 일시
- 최근 활동 요약 카드(최근 업로드 결과 등)
- BOM 업로드 박스를 홈 화면에 배치 (별도 업로드 탭 없음 — 프로토타입 단계에서 확정된 방향 계승)

### 4.3 BOM 조회·입력 (핵심 화면)
- 상단 필터바: 국가 선택 / 상태(완료·미입력) / 검색(품번·품명) — 기존 그리드 필터 로직 계승
- 데이터 그리드: HTMX로 필터 변경 시 부분 갱신(전체 리로드 없음). 서버사이드 페이지네이션 적용(990행 전체를 한 번에 렌더링하지 않음 — Streamlit data_editor와 달리 HTMX 방식은 페이지 단위 필요)
- 셀 인라인 편집 → 저장 시 해당 행만 HTMX로 갱신, 재료비/총합계 자동계산 값 즉시 반영
- 그리드 하단 요약바(표시건수/재료비합계/총합계합계) 유지

### 4.4 환율 관리 / 다운로드
- 사이드바 하단 위젯 형태 유지(환율 카드 + 수동갱신 버튼, 다운로드 버튼) — 별도 탭 불필요하다는 기존 결정 계승

### 4.5 로그인 화면
- 별도 심플 로그인 페이지(아이디/비밀번호), 로고+포탈명
- 미인증 상태로 접근 시 전체 라우트가 로그인 페이지로 리다이렉트

## 5. 에러 처리 (기존 PRD 승계 + 신규)

기존 PRD 5장(업로드 시트 구조 상이 / 품번 중복·공백 / 환율 API 실패 / 계산 결측 / 템플릿 손상)은 그대로 유지. 신규 추가:

| 상황 | 처리 |
|---|---|
| 로그인 실패 | 에러 메시지 표시. 계정 잠금 없음(관리자 1계정 규모라 불필요) |
| 세션 만료 | 로그인 페이지로 리다이렉트 |
| HTMX 부분 갱신 요청 실패 | 화면에 토스트 에러 표시 + 전체 새로고침 유도 문구 |

## 6. 테스트 계획

- 기존 pytest 스위트(23개)를 새 복합키 구조에 맞게 갱신 후 전체 통과 확인
- 신규: 로그인/로그아웃/세션보호 라우트 테스트
- 신규: 복합키 upsert 테스트 — 동일 품번이 여러 행에 존재하는 케이스(실제 BOM의 74개 중복 품번 패턴 재현) 포함
- 실제 `BOM 양식.xlsx`로 업로드 → 조회/필터 → 인라인 편집 → 다운로드 전체 플로우 수동 브라우저 검증

## 7. Out of Scope (이번 마이그레이션 제외, 로드맵 PHASE1 정식판/이후 확장)

- 재료비 SUMMARY(품목군별 Sub total, 총재료비 Grand total)
- 다중 사용자 동시 입력, 관리자/설계자 권한 분리 (users.role 컬럼은 확보하되 로직 미구현)
- 로드맵 PHASE1의 추가 필드(소싱정보-생산지역/공장/MIP·LP·KD, 물류정보-작업수량/포장비/운임/관세율 상세, 차종정보-SOP/환율기준/원자재기준)
- PHASE2~5 (버전관리/잠금, 목표가 관리, 약정인하/원자재 연동, 시점별 비교분석)
- 사내서버/클라우드 배포 (이번은 로컬 PC 실행 유지)
